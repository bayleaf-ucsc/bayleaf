# Qwen3.8-27B scale-to-zero practice run

Issue: https://github.com/bayleaf-ucsc/bayleaf/issues/75

This is an operator log for synthetic text only. No BayLeaf API routing or user data is involved.

## Outcome

On-demand H200 from an 18.48 GB **runtime-only** snapshot plus on-boot weight download reached first token in **139.6 and 140.6 seconds** on two fresh, immediately repeated boots. Allocation took 1–2 seconds, weights 19–20 seconds, and vLLM initialization about 117 seconds. Each boot cost an estimated **$0.22** at the listed H200 on-demand rate and ended in confirmed sandbox deletion. These same-evening boots prove GPU scale-to-zero, but do not establish latency after several days of provider cache decay.

The runtime+weights snapshot failed Daytona's 20 GB image cap at **38.09 GB**; the stock `daytona-gpu` snapshot lacks disk/RAM and rejects resource overrides. Even the runtime-only snapshot has just ~1.52 GB of headroom beneath that cap, so an unpinned future vLLM image could stop building. vLLM 0.28.0 on Daytona's 5090 host failed on its older CUDA driver, so the successful service data uses an H200; do not extrapolate its throughput or GPU cost to a 4090/5090. Separate eager-mode tuning reached first token in **101.4 seconds**, but cut single-stream output from about 100 to 16–18 tokens/s. For this pinned stack, the feasible packaging route is runtime-only snapshot plus checkpoint transfer, with normal vLLM settings if sustained interactive output matters.

All experiment sandboxes and snapshots were explicitly deleted and their absence verified. No BayLeaf route or production deployment was made. The scripts and log are retained on an experiment branch for future bootstrapping; the results are reported on issue #75.

- Repeatable boot driver: with `DAYTONA_API_KEY` in the environment or `~/.tokens/daytona-api`, run `uv run --script api/scripts/qwen38/run.py SNAPSHOT_NAME --output /path/to/local/qwen38-boot.json`. It records timestamps as it runs, has 15-minute allocation and 10-minute health deadlines, and deletes its own sandbox in `finally`. Output is operator-local and contains no credentials or prompt content.
- `--eager` is an explicit *separate* startup optimization arm (`--enforce-eager` in vLLM), not part of the fixed-parameter packaging comparison. [vLLM documents](https://docs.vllm.ai/en/stable/configuration/optimization/) that it skips compilation and CUDA-graph capture for faster startup at a steady-state decode cost. Benchmark throughput and prefix hits again because it changes serving behavior.

## Comparison protocol

1. Stock `daytona-gpu`: infeasible for this checkpoint as documented (1 vCPU, 1 GiB RAM, 1 GiB disk). The API rejects explicit resource overrides alongside `snapshot`; a 21 GB checkpoint cannot fit. The custom pinned-image pilot substitutes for *operational* from-scratch work, but it must not be reported as the stock-snapshot arm.
2. Prebuilt GPU snapshot with vLLM runtime and launch configuration only: download weights at each fresh boot.
3. Prebuilt GPU snapshot with the same runtime and checkpoint: **blocked** at snapshot creation. Daytona rejected the 38.09 GB image against a 20 GB hard limit. A materially different, smaller model/runtime might fit, but that would not be the same pinned comparison. Never capture transient prompts or outputs in a reusable snapshot.

For each arm, timestamp wake request, build/snapshot acquisition, allocation, weight transfer, process launch, VRAM load, first healthy model response, streamed first token, teardown request and confirmed deletion. Separate image/snapshot build time and any artifact cost. Record repeated fresh boots and cache locality; no loaded process or KV survives deletion. Use identical synthetic prompts and measure 1/2/4 concurrent requests, shared-prefix turns, memory/disk peak, context limit, and overload. The two-week inactive-snapshot activation case was not tested.

**Decision target:** request-to-first-token after several days without a running GPU. Tonight's immediate fresh boots measure snapshot acquisition and vLLM cold load but may benefit from recent image/checkpoint caches. A 3-day-idle wake and the 14-day inactivity/activation case would require follow-ups; Adam chose not to probe cache decay now, so all named snapshots were deleted. Inactivity with **no snapshot** has no experiment-specific GPU or snapshot storage cost, but also requires paying the one-time build again before the next boot. Actual snapshot storage charges were not obtained; use the published disk rate only as an estimate, not an invoice.
