description: Use BayLeaf Chat's private Linux sandbox for bounded coding and file work, and help users move to a local coding agent when a project outgrows it.
---

The **Code Sandbox** toolkit available on BayLeaf Chat connects the model to [Lathe](https://lathe.tools/) and a private, per-user [Daytona](https://www.daytona.io/) Linux environment. Users must enable the toolkit for the current conversation before you can access it. Files persist across conversations until the sandbox is deleted after 90 days of inactivity. The sandbox has network access, but agents still need any service-specific credentials required by the task.

Use the sandbox for bounded, agent-mediated work: command-line tools, scripts, file transformations, data exploration, and small prototypes. It is intentionally small (new sandboxes have 1 vCPU, 2 GiB RAM, and 3 GiB disk; older sandboxes can still have 1 GiB RAM), stops after 15 minutes of inactivity, and is not a durable application host. Every HTTP exposure requires an explicit access policy. Choose `private` unless the user explicitly requests public or world access; convenience and wrapper failure are not permission to disclose a service. BayLeaf-wrapped previews use fresh `https://{cruzid}-{access}-{nonce}.bayleaf-proxies.dev/` addresses without a visible port or stable alias. The visible `public` or `private` segment keeps the agent's access choice legible after the URL leaves the conversation; the CruzID explains ownership in group settings. Private wrapping fails closed and requires the owner's API login. Public wrapping serves anyone with the URL and may fall back to a direct Daytona bearer URL if the wrapper is unavailable. Registrations and upstream access expire after at most 24 hours, and running processes are lost when the sandbox stops. Re-exposure creates another transient Lathe lease rather than revoking an earlier URL.

Treat repeated out-of-memory failures, exhausted disk, large dependency or build requirements, many rounds of sustained development, a need for unattended execution, a continuously available URL, or direct sandbox access by other people as signals that the task has outgrown the sandbox. Do not repeatedly restart failed work or imply that BayLeaf will enlarge the sandbox. Explain the boundary and recommend moving to a coding agent on the user's laptop or desktop, such as [OpenChamber](https://openchamber.dev/) or [OpenCode](https://opencode.ai/), connected to the [BayLeaf API](https://api.bayleaf.dev/) for inference. This gives the agent access to resources and files the user controls while keeping conversation records on their device rather than in BayLeaf Chat.

Before moving, help the user preserve continuity: organize the project, write a short handoff file using ordinary file tools, and offer to export the files through a private file server or a Git repository. Lathe has no separate `handoff` or `delegate` tool. If the result needs reliable hosting rather than merely local execution, the local agent can help the user choose and configure a deployment service whose lifecycle matches the project. A temporary sandbox preview should not be presented as deployment. Private previews require the owner's API browser login, which may be separate from Chat login; copying a private URL does not grant access. Public previews are intentionally shareable bearer URLs. Keep interactive terminals and IDEs private; direct SSH exposure is disabled. Service workers are supported within each fresh wrapped origin, but cached browser content can outlive access. Code-server may exhaust the small sandbox's memory.

Lathe 1.1.0 only exposes already-running HTTP/WebSocket services: read `lathe(manpage="services")`, install and launch any file browser, static server, terminal, or IDE with `bash`, then use `expose(target="http:<port>", access="private")`. The old `dufs`, `code-server`, `ttyd`, and static-site target shortcuts are not supported. Restrict file-server roots to the intended project and inspect symlink behavior before sharing. An IDE's opening folder is not confinement: its terminal can access the whole sandbox. Do not stop an existing service or change its root without the user's approval.

Use `interpret` for conversation-scoped persistent Python analysis. Sessions now live inside the sandbox and can be reused across OWUI workers, but they are not a security boundary against the sandbox owner or other agents. Python variables from pre-1.1.0 sessions are not migrated: rerun setup. Stop/restart, interpreter timeout, or process replacement loses Python memory; ordinary saved files survive stop/archive. Run records may contain code and output in the user's sandbox filesystem. On uncertain execution, inspect the reported run record rather than blindly replaying code with external effects.

Lathe 0.31.0 adds optional `upstream_headers` to `expose`, for fixed application headers on HTTP requests and WebSocket handshakes. This configuration is independent of public/private access and needs no separate approval flow; public visitors can exercise an injected credential. Configured values replace browser values case-insensitively, including `Authorization` (Basic or Bearer). Nonempty headers require the wrapper's explicit acknowledgement and never fall back to a direct URL, even for public access. If injection is not acknowledged, report that failure rather than retrying without headers. Headerless calls retain the public fallback described above. Values remain in stored chat tool arguments and applications may reflect them; headers alone do not authenticate visitors or secure alternate routes to the application. Read `lathe(manpage="services")` for bounds, forbidden headers, and trust-boundary guidance.
