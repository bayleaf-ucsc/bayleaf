description: Use BayLeaf Chat's private Linux sandbox for bounded coding and file work, and help users move to a local coding agent when a project outgrows it.
---

The **Code Sandbox** toolkit available on BayLeaf Chat connects the model to [Lathe](https://lathe.tools/) and a private, per-user [Daytona](https://www.daytona.io/) Linux environment. Users must enable the toolkit for the current conversation before you can access it. Files persist across conversations until the sandbox is deleted after 30 days of inactivity (90 days before 2026-11-14). The sandbox has network access, but agents still need any service-specific credentials required by the task.

Use the sandbox for bounded work: command-line tools, scripts, file transformations, data exploration, and small prototypes. New workspaces reserve 1 vCPU, can burst to 2 vCPUs, and have 2 GiB RAM and a 10 GiB disk cap. Imported workspaces keep their existing sizes. Workspaces pause after one hour idle, and work does not progress until they resume. They are not durable application hosts. Every HTTP exposure requires an explicit access policy. Choose `private` unless the user explicitly requests public or world access. BayLeaf-wrapped previews use fresh `https://{cruzid}-{access}-{nonce}.bayleaf-proxies.dev/` addresses. Private wrapping fails closed and requires the owner's API login. Public wrapping serves anyone with the URL and may fall back to a direct Daytona bearer URL if the wrapper is unavailable. Registrations expire after at most 24 hours. Re-exposure creates another temporary lease rather than revoking an earlier URL. To delete a workspace, direct the owner to the BayLeaf API dashboard.

Treat repeated out-of-memory failures, exhausted disk, large dependency or build requirements, many rounds of sustained development, a need for unattended execution, a continuously available URL, or direct sandbox access by other people as signals that the task has outgrown the sandbox. Do not repeatedly restart failed work or imply that BayLeaf will enlarge the sandbox. Explain the boundary and recommend moving to a coding agent on the user's laptop or desktop, such as [OpenChamber](https://openchamber.dev/) or [OpenCode](https://opencode.ai/), connected to the [BayLeaf API](https://api.bayleaf.dev/) for inference. This gives the agent access to resources and files the user controls while keeping conversation records on their device rather than in BayLeaf Chat.

Before moving, help the user preserve continuity: organize the project, write a short handoff file using ordinary file tools, and offer to export the files through a private file server or a Git repository. Lathe has no separate `handoff` or `delegate` tool. If the result needs reliable hosting rather than merely local execution, the local agent can help the user choose and configure a deployment service whose lifecycle matches the project. A temporary sandbox preview should not be presented as deployment. Private previews require the owner's API browser login, which may be separate from Chat login; copying a private URL does not grant access. Public previews are intentionally shareable bearer URLs. Keep interactive terminals and IDEs private; direct SSH exposure is disabled. Service workers are supported within each fresh wrapped origin, but cached browser content can outlive access. Code-server may exhaust the small sandbox's memory.

`expose` only exposes already-running HTTP/WebSocket services: read `lathe(manpage="services")`, launch the service on an interface reachable by the proxy (for example, `0.0.0.0`), then use `expose(target="http:<port>", access="private")`. Keep terminal, IDE, and VNC previews private. Restrict file-server roots to the intended project and inspect symlink behavior before sharing. An IDE's opening folder is not confinement: its terminal can access the whole sandbox. Do not stop an existing service or change its root without the user's approval.

Use `interpret` for conversation-scoped persistent Python analysis. Sessions live inside the sandbox and can be reused across OWUI workers, but they are not a security boundary against the sandbox owner or other agents. A pause keeps files, processes, and Python memory, though network connections may need to reconnect. A restart, interpreter timeout, or replacement loses Python memory. Imported workspaces keep archived files but not live processes or Python memory from v0. Run records may contain code and output in the user's sandbox filesystem. On uncertain execution, inspect the run record before replaying code with external effects.

Browser headers that an app's own pages send (CSRF markers, API-version headers) already pass through the BayLeaf preview gateway, and app error bodies come back unless they are large or name the upstream. Do not use `upstream_headers` to make forwarding work, and never inject a CSRF marker: that disables the app's own check. `upstream_headers` is only for fixed values the browser cannot hold, such as `Authorization` for an app with no login. With `access="public"` it also requires `public_headers_acknowledged=true`, set only after the user approves letting anyone with the URL use those values. Injection must be acknowledged by the gateway and never falls back to a direct URL; if it fails, report that rather than retrying without headers. Values stay in stored chat tool arguments. Read `lathe(manpage="services")` for limits.
